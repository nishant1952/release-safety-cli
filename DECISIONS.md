## Signals
- Reversibility: rules on added lines of code files only. "Persisted writes (the gate 3 detector)" are gate 3's destructive hits; additive DDL and row-scoped CRUD do not make a change irreversible. An HTTP call (`fetch`, `axios`, `got`, `ky`, `http(s).request`) is classified by its first argument: a literal or template starting with `/api` is internal, one starting with `http(s)://` is an external API client. An identifier (or a template's leading identifier) is resolved one hop with ts-morph to its variable declaration's literal or template. A target that still is not resolved keeps the change irreversible, and the note says "target not resolved", not "external API client". Additive DDL such as `CREATE TABLE IF NOT EXISTS` stays reversible (user-confirmed).
- Feature flag: only `getBooleanValue(key, default)` calls and `@fireweave-controlpoint` anchors count as flags. Each added line is classed control (reads or configures the flag), inside (either branch of a flag conditional/if/&&, or after an `if (!flag) return` guard in a same-file component the flag is passed to as a prop), or outside. Blank, comment and bracket-only lines are not classed; non-TS files (CSS) are outside. Value: none / partial (any outside line) / full.
- Feature flag: "flag exists in production", "both states tested" and "kill path works" (W appendix) need a flag service and tests; they are named as unchecked in the note rather than guessed.
- Path: entry points are files run by a workspace package.json script (`bun|node|tsx|ts-node <file>`) or loaded by a package's index.html `<script src>`. Imports resolve relative paths and workspace package names only; external packages are not followed. "live" means at least one changed file reaches an entry point; per-file chains and unreached files are listed. Inside TSX files, components are followed by JSX usage up to a `<Route element=...>` in the same file. Traces (W appendix) are not available, so callers are static only.
- Path provenance: the import graph and routes are measured from code, but entry points come from package.json/index.html, so the path value is tagged declared; with no entry points it is live, assumed (W 2).
- Reach: calls on added lines outside apps/api are followed through definitions (depth ≤ 4, repo files only) until a `/api/...` literal is found; each endpoint maps to the apps/api handler `path === "<endpoint>"` and the `services.x.y()` calls and imported functions in its block. Org-wide search for topics, tables and cache keys (W appendix) is not done.
- Reach worth: the metrics catalog has no `tier` field at c5da112a. A tier applies when a catalog entry's `source` names a reached call; any non-"low" tier counts as high. With no applicable tier the reach is high, assumed (W 2 "the reach is wide").
- Failure mode: first-match rules on each changed file's path (docs/tests, then security, then infra, then domain); the value is the set over the change. Infra paths include `infrastructure/`, `observability/`, `fireweave/` (the flag harness), CI, Docker, scripts and manifests. CSS and UI components are domain.

## Write-up contradictions, resolved in code (writeup.md is frozen)

Section 3, example row 1: "Adding logs for more visibility | Infra | Low | Fast (revert or flag) | ... | Auto". Resolution: undo speed is measured, not categorical. A flag covering the whole change is fast. Mixed failure modes need a detector for each. Missing or unknown rounds to slow (W 2). The ignore case "Auto mode needs only the deploy health check" is the infra branch of this rule, not a separate rule.

## Round 3: measurement fixes and the model contract

### Unit 1: flag coverage follows call sites
- A top-level declaration in a changed TS file that contains at least one added line (function, class, variable, type, interface, enum, or the import bindings that are new since base) is a call-site candidate. ts-morph finds its references at head; references inside its own span (the name, recursion) and import specifiers (they only re-bind the name) are not call sites. Import bindings count references in their own file only.
- A candidate is inside when every reference sits in a flag range or in the span of a candidate already classed inside, repeated to a fixed point. Its lines that would be "outside" become inside. Lines still outside keep the old class.
- A candidate whose every reference is on a flag-read line (the `getBooleanValue` call or its declaration, or an anchor or key line) is flag plumbing and classed control, e.g. the flag client's import. Other control lines (a prop or guard that passes the flag on) do not count as inside references: `<Menu enabled={flag} />` renders Menu for everyone.
- Zero references: an unexported declaration with none is inside (it never runs). An exported declaration with none stays outside: an entry point, a framework page or a package export runs with no reference in the repo. This narrows the brief's "zero references outside the flag count as inside" to unexported declarations.
- Import lines: a new binding used only inside the flag classes the import line inside. This is a small leniency: importing a module the file did not import before still runs that module's load-time code with the flag off. That code is in its own file, where its own added lines are classed by the same rules.
- A declaration that runs code when its module loads (a call, `new`, tagged template or decorator outside every function body, e.g. `const x = createContext(false)`) is not moved: it runs whether the flag is on or off.
- Exported candidates need references from any file, so the rest of the repo's TS files at head are loaded only when one exists.
- Effect on arcade: no flag goes partial -> full. Every flagged PR still has outside lines that run with the flag off: styles.css edits (all of 13, 14, 17, 18, 19, 21; CSS still counts, Unit 2), components rendered unconditionally whose hooks run before the flag guard (PR 13 ProfileMenu, apps/web/src/App.tsx:404-426), the pins routes, repo and use cases that the flag does not gate (PR 17-19), and flag values passed through React context, which the tracer does not follow (PR 14). PR 13 moves 2 lines: `import { fw }` (control) and `import { metric as record }` (inside); inside 85 -> 86, control 6 -> 7, outside 98 -> 96.

### Unit 2: non-code files are not a live path
- Non-code kinds (src/files.ts, first match wins): editor config (`.cursor/`, `.claude/`, `.vscode/` at any depth), docs (`*.md`, `*.txt`), stylesheets (`*.css`, `*.scss`), lockfiles (npm, yarn, pnpm, bun), workflow YAML (`.github/workflows/*.yml`, `.gitlab-ci.yml`), compose YAML (`compose*.yml`, `docker-compose*.yml`), shell scripts under a `scripts/` directory. Anything else may be code, including `package.json` and a shell script outside `scripts/`.
- When every changed file (deleted ones included) is non-code: Path = "not a code path" (measured) and Reach = "none" (measured), so damage is low. In a mixed change, path chains and reach are computed on the code files only, and the non-code files are listed in both notes with their kind.
- Failure mode per file: docs and editor config -> none (they do not run in production), stylesheets -> cosmetic, lockfiles, workflow and compose YAML and scripts -> infra (they change the build or the deploy; the brief named failure modes only for docs and stylesheets, so these keep the existing rule). The signal's value comes from the code files when there are any (PR 13 stays "domain, infra", styles.css is listed as cosmetic), then "cosmetic", then "none".
- Cosmetic is not one of the write-up's three modes and needs no detector: a broken style is seen by people, not by an error rate. A stylesheet-only change therefore has no detector to find. This supersedes the earlier "CSS and UI components are domain".
- Flag line count: stylesheets still count (Unit 2 brief), and so do lockfiles, CI, compose and scripts, because no flag turns them off. Docs and editor config lines are not classed: they never run, so they are neither inside nor outside a flag.
- Flag advice ("adding a flag would move the grid ...") is not given when the path is "not a code path": no flag can wrap a README or a workflow file.
- Effect: PR 3 Human -> Staged, PR 6 and PR 12 stay Staged (now measured instead of "unreached, declared"). PR 4 Human -> Staged, not Auto: low damage, but the window is long because undo is a full build and deploy (time to revert assumed, rounded to slow by W 2), and nothing in this unit shortens it. PR 10 stays Human: apps/web/src/games/meta.ts is a TS file on a live path (it holds theme colour data, which is cosmetic in effect, but no rule here reads a code file's content as cosmetic). Its two stylesheets are listed only.

### Unit 3: removed-and-re-added is a move
- Source: the Round 3 brief, not writeup.md. W 1a items 2 and 3 say only that breaking and destructive changes trip; the write-up has no sentence about moves.
- A statement removed in one place and added in any file of the same diff, whitespace normalised, is a move: it does not trip gate 2, gate 3 or the persisted-write rule, and the gate lists it under "moved routes and exports" or "moved schema statements" as "moved from <old path> to <new path>", with both lines as evidence.
- "The same statement" depends on the kind: for SQL (CREATE TABLE, ALTER TABLE, DROP, TRUNCATE, ADD COLUMN, DELETE, UPDATE), the whole statement from its keyword to its closing backtick or semicolon, read from the file at base or head; for a route, the route line; for an export, its signature (value or body ignored, as gate 2 already compares). A table re-created under the same name with different columns is therefore not a move. Routes and exports are weaker evidence: a route whose handler body changed, or an `export const x = {` whose contents changed, still counts as moved. The gate note says so.
- The rule runs both ways: a removed CREATE TABLE or ADD COLUMN found among added lines, and an added destructive statement (DROP, ALTER, unscoped write) found among removed lines. The exception: an added destructive statement in a migration or SQL file still trips even when it was removed elsewhere, because migration tools key on file names and a moved migration can run again.
- A moved export or route is not "additive API surface" at its new location.
- Effect: PR 5 records 8 routes moved from server/src/index.ts to apps/api/src/interfaces/http/router.ts and 7 exports moved, but gate 2 still trips on five routes that are really gone (/api/metrics/streams, /api/game, /api/game/new, /api/game/move, /api/stats) and on exports not re-added. Gate 3 still trips, and reversibility still cites server/src/db.ts@549a1bc:32: `CREATE TABLE IF NOT EXISTS games` is replaced by `CREATE TABLE IF NOT EXISTS matches` with different columns, and no added line re-creates `games`. That is a replacement, not a move, so the expected "PR 5 gate 3 passes" does not hold. PR 7 records moved engine exports. No mode changes.

### Unit 4: public contract means public
- A removed or changed export breaks the contract only when its module is reachable from outside the repo: a schema file (name has schema, catalog, openapi or swagger, or .proto/.graphql/.avsc, as before), or a module of a published package, which is the nearest package.json at base without `"private": true`. In a published package, the public modules are the targets of "exports", "main", "module" and "types" (a build path such as `dist/x.js` stands for `src/x`), plus the files those entries re-export with `export ... from`, followed transitively. A published package with no "exports" map exposes every file, because any path can be deep-imported. "module" and "types" and the dist-to-src mapping go beyond the brief's "exports"/"main"; they are added so a TS package whose main points at build output is still read correctly.
- A removed route is always breaking (it is reachable over HTTP) unless it moved (Unit 3). Removed lines of a schema file trip as before.
- Wildcard subpaths in "exports" (`"./*": "./src/*.ts"`) are matched as patterns.
- Every other removed or changed export is listed as the gate 2 check "internal signature changes" (pass, declared, since it rests on package.json), with each line and the reason per file. It does not trip the gate. "Every other" means: a private package, a module outside every package when the repo has other manifests, or a non-entry module of a published package.
- When reach cannot be read, the export is listed under "export reachability" (unverifiable, assumed) and routes to a human, never passing silently (W 2): no repo, an owning package.json that does not parse, or a repo with no package.json at all.
- "Lower confidence one notch" lowers the reported confidence one step, and the reason is listed. The measured level, which alone can shift the mode (W 2), is not touched. applyPolicy takes these as `notches`, and Unit 5 reuses them.
- Effect: PR 1 (server/src/metrics.ts, private `server`) and PR 7 (packages/engine-suite, private) now pass gate 2, and both stay Human on the grid. PR 5 is unchanged: it removes five routes. PR 9 does not pass gate 2, unlike the expectation: its one export (apps/api/src/infrastructure/observability/openobserve.ts@504f75e:245, private `@arcade/api`) is now internal, but it also edits entries in the metrics catalog, which the gate 2 ruling above treats as an event schema. Its mode is unchanged.

### Unit 5: required CI checks are measured, not assumed
- `bun run export` (src/export.ts) writes required-checks.json beside pr.json: `{ "checks": [...], "source": "..." }`. The checks are the union of branch protection's `required_status_checks` (contexts and checks) and repository rules of type `required_status_checks` on the PR's base branch. `GET .../branches/{base}/protection` needs admin rights; when it is refused, the readable `GET .../branches/{base}` summary (its `protection.required_status_checks`) is used instead. `source` records each endpoint's answer. The file is not written when no endpoint answers, so the brief falls back to the old assumed behaviour instead of reading "no answer" as "none required". For tests, a fixture `x.json` takes its required set from `x.required-checks.json`.
- The required set is today's configuration, read at export time, not the configuration when the PR ran. The export does not show past branch settings.
- Gate 1, with a rollup and a required set: a required check that is red trips and blocks (measured). A required check that is pending or absent from the rollup is unverifiable and routes to a human. An empty set gives "no required checks configured" (measured), and CI cannot block. Red checks that are not required are listed as "advisory CI checks" (pass, declared, from the rollup). Each lowers the reported confidence one notch (not the measured level), and each becomes a brief reason whose basis is named (the rollup and required-checks.json), not "something missing".
- Green for a required check means SUCCESS, NEUTRAL or SKIPPED, because GitHub counts all three as passing a required check. The brief said "conclusion other than SUCCESS"; this follows GitHub's merge rule instead. A check still running (conclusion empty, or state PENDING or EXPECTED) is pending.
- No required-checks.json: as before, every rollup check is treated as required, now tagged assumed. No rollup: unverifiable, routed to a human, as before.
- Effect: all 21 arcade exports have required-checks.json with no required checks (`main` is unprotected and has no rules). PR 11, 15, 16 and 20 go Block -> Human: their red "flag contract" and "rollout readiness" checks are advisory, and the grid (high damage x long window) gives Human. PR 11's gate 1 still routes to a human, for its hardcoded URLs, not for CI. PR 13's CI check goes from declared to measured.

### Unit 6: the model may fill an assumed signal with a cited one
- **Deviation from the write-up's one-way rule.** W 2 says missing data rounds toward caution, and W 3 says the probability shift "never moves the other way". Here a model answer may move an assumed signal one step either way, including toward release. The argument: the write-up rounds *missing* data toward caution; a line cited from the diff or the repo, which code has checked exists, is not missing data; the one-way rule still holds for measured facts, which the model never sees or changes. Confidence still only moves down from a model answer, never up.
- Accepted proposals feed the decision like any signal, so a Reach or Detection move can loosen the mode, e.g. high to low reach can take a change from Human to Staged. Code checks that a citation exists (and that a base-side cite names this diff's base), not that it supports the claim. The relevance check is the model's one sentence, shown beside the citation in the brief for the human to judge.
- The note of an assumed signal is sent as its "why assumed". Some notes quote measured facts, e.g. the Reach note names the endpoints the calls reach. The model sees those facts as context; it cannot change any measured signal.
- One call (purpose "model contract") replaces the separate failure-mode and coherence calls. Input: the diff with head line numbers (base numbers for removed lines), the base sha, the PR title, body and commit message, and the assumed signals that have a scale, each with its value, scale and why it is assumed. Measured and declared signals, gate results and the mode are not sent. Output (strict JSON schema): `proposals[]` (signal, "no change" or "propose", value, cite, reasoning), `failure_modes` {modes, reason} and `coherence` {coherent, mismatches}. Reason wording (two sentences per evidenced reason) stays a separate call: it was not one of the two reads.
- Scales (src/policy.json `model.scales`, cautious to favourable): Path live < unreached; Reach high < low < none; Detection apparatus slow < fast; Time to revert full build and deploy < one-click rollback. "measured pipeline under 15 minutes" is left off the time-to-revert scale, because a cited line cannot measure a duration (CI run history is not an input). An assumed signal with no scale (History, review depth, the LLM reads themselves) is not offered to the model, and a proposal for it is refused.
- Code accepts a proposal only if the signal is assumed, the value is on its scale, the value is within one step of the current one, the cited `path:line` (head) or `path@sha7:line` (base) resolves to a non-blank line, and it is the first proposal for that signal. Accepted: the value is replaced, the source becomes "model (cited)", the evidence is the citation (quoted in the brief) and the note keeps the reasoning and the old assumed value. Refused: listed under Disagreements with the reason, and like every disagreement it lowers confidence one step.
- The model sees values after the missing-data policy has rounded them, as the brief shows them. Confidence is computed from the signals before accepted proposals are applied, so filling an assumed input never raises it. The one-unknown search flips only assumed signals, so a signal the model filled is no longer offered as the unknown.
- No API key, or a secret found by gate 1: no call. Every assumed signal stays assumed, both reads are "unavailable", and the brief is unchanged (the golden out/pr13-brief.md is rendered without a key).

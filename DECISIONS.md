An identifier (or a template's leading identifier) is resolved one hop with ts-morph to its variable declaration's literal or template. A target that still is not resolved keeps the change irreversible, and the note says "target not resolved", not "external API client". Additive DDL such as `CREATE TABLE IF NOT EXISTS` stays reversible (user-confirmed).
- Feature flag: only `getBooleanValue(key, default)` calls and `@fireweave-controlpoint` anchors count as flags. ## Round 3: measurement fixes and the model contract

### Unit 1: flag coverage follows call sites
- A top-level declaration in a changed TS file that contains at least one added line (function, class, variable, type, interface, enum, or the import bindings that are new since base) is a call-site candidate. ts-morph finds its references at head; references inside its own span (the name, recursion) and import specifiers (they only re-bind the name) are not call sites. Import bindings count references in their own file only.
- A candidate is inside when every reference sits in a flag range or in the span of a candidate already classed inside, repeated to a fixed point. Its lines that would be "outside" become inside. Lines still outside keep the old class.
- A candidate whose every reference is on a flag-read line (the `getBooleanValue` call or its declaration, or an anchor or key line) is flag plumbing and classed control, e.g. the flag client's import. Other control lines (a prop or guard that passes the flag on) do not count as inside references: `<Menu enabled={flag} />` renders Menu for everyone.
- Zero references: an unexported declaration with none is inside (it never runs). An exported declaration with none stays outside: an entry point, a framework page or a package export runs with no reference in the repo. This narrows the brief's "zero references outside the flag count as inside" to unexported declarations.
- Import lines: a new binding used only inside the flag classes the import line inside. This is a small leniency: importing a module the file did not import before still runs that module's load-time code with the flag off. That code is in its own file, where its own added lines are classed by the same rules.
- A declaration that runs code when its module loads (a call, `new`, tagged template or decorator outside every function body, e.g. `const x = createContext(false)`) is not moved: it runs whether the flag is on or off.
- Exported candidates need references from any file, so the rest of the repo's TS files at head are loaded only when one exists.
- Effect on arcade: no flag goes partial -> full. Every flagged PR still has outside lines that run with the flag off: styles.css edits (all of 13, 14, 17, 18, 19, 21; CSS still counts, Unit 2), components rendered unconditionally whose hooks run before the flag guard (PR 13 ProfileMenu, apps/web/src/App.tsx:404-426), the pins routes, repo and use cases that the flag does not gate (PR 17-19), and flag values passed through React context, which the tracer does not follow (PR 14). PR 13 moves 2 lines: `import { fw }` (control) and `import { metric as record }` (inside); inside 85 -> 86, control 6 -> 7, outside 98 -> 96.

### Unit 2: non-code files are not a live path
- Non-code kinds (src/files.ts, first match wins): editor config (`.cursor/`, `.claude/`, `.vscode/` at any depth), docs (`*.md`, `*.txt`), stylesheets (`*.css`, `*.scss`), lockfiles (npm, yarn, pnpm, bun), workflow YAML (`.github/workflows/*.yml`, `.gitlab-ci.yml`), compose YAML (`compose*.yml`, `docker-compose*.yml`), shell scripts under a `scripts/` directory. Anything else may be code, including `package.json` and a shell script outside `scripts/`.
- When every changed file (deleted ones included) is non-code: Path = "not a code path" (measured) and Reach = "none" (measured), so damage is low. In a mixed change, path chains and reach are computed on the code files only, and the non-code files are listed in both notes with their kind.
- Failure mode per file: docs and editor config -> none (they do not run in production), stylesheets -> cosmetic, lockfiles, workflow and compose YAML and scripts -> infra (they change the build or the deploy; the brief named failure modes only for docs and stylesheets, so these keep the existing rule). The signal's value comes from the code files when there are any (PR 13 stays "domain, infra", styles.css is listed as cosmetic), then "cosmetic", then "none".
- Cosmetic is not one of the write-up's three modes and needs no detector: a broken style is seen by people, not by an error rate. A stylesheet-only change therefore has no detector to find. This supersedes the earlier "CSS and UI components are domain".
- Flag line count: stylesheets still count (Unit 2 brief), and so do lockfiles, CI, compose and scripts, because no flag turns them off. Docs and editor config lines are not classed: they never run, so they are neither inside nor outside a flag.
- Flag advice ("adding a flag would move the grid ...") is not given when the path is "not a code path": no flag can wrap a README or a workflow file.

PR 4 Human -> Staged, not Auto: low damage, but the window is long because undo is a full build and deploy (time to revert assumed, rounded to slow by W 2), and nothing in this unit shortens it. PR 10 stays Human: apps/web/src/games/meta.ts is a TS file on a live path (it holds theme colour data, which is cosmetic in effect, but no rule here reads a code file's content as cosmetic). ### Unit 3: removed-and-re-added is a move
- Source: the Round 3 brief, not writeup.md. W 1a items 2 and 3 say only that breaking and destructive changes trip; the write-up has no sentence about moves.
- A statement removed in one place and added in any file of the same diff, whitespace normalised, is a move: it does not trip gate 2, gate 3 or the persisted-write rule, and the gate lists it under "moved routes and exports" or "moved schema statements" as "moved from <old path> to <new path>", with both lines as evidence.
- "The same statement" depends on the kind: for SQL (CREATE TABLE, ALTER TABLE, DROP, TRUNCATE, ADD COLUMN, DELETE, UPDATE), the whole statement from its keyword to its closing backtick or semicolon, read from the file at base or head; for a route, the route line; for an export, its signature (value or body ignored, as gate 2 already compares). A table re-created under the same name with different columns is therefore not a move. Routes and exports are weaker evidence: a route whose handler body changed, or an `export const x = {` whose contents changed, still counts as moved. The gate note says so.
- The rule runs both ways: a removed CREATE TABLE or ADD COLUMN found among added lines, and an added destructive statement (DROP, ALTER, unscoped write) found among removed lines. The exception: an added destructive statement in a migration or SQL file still trips even when it was removed elsewhere, because migration tools key on file names and a moved migration can run again.
- A moved export or route is not "additive API surface" at its new location.
- Effect: PR 5 records 8 routes moved from server/src/index.ts to apps/api/src/interfaces/http/router.ts and 7 exports moved, but gate 2 still trips on five routes that are really gone (/api/metrics/streams, /api/game, /api/game/new, /api/game/move, /api/stats) and on exports not re-added. Gate 3 still trips, and reversibility still cites server/src/db.ts@549a1bc:32: `CREATE TABLE IF NOT EXISTS games` is replaced by `CREATE TABLE IF NOT EXISTS matches` with different columns, and no added line re-creates `games`. That is a replacement, not a move, so the expected "PR 5 gate 3 passes" does not hold. PR 7 records moved engine exports. No mode changes.

### Unit 4: public contract means public
- A removed or changed export breaks the contract only when its module is reachable from outside the repo: a schema file (name has schema, catalog, openapi or swagger, or .proto/.graphql/.avsc, as before), or a module of a published package, which is the nearest package.json at base without `"private": true`. In a published package, the public modules are the targets of "exports", "main", "module" and "types" (a build path such as `dist/x.js` stands for `src/x`), plus the files those entries re-export with `export ... from`, followed transitively. A published package with no "exports" map exposes every file, because any path can be deep-imported. "module" and "types" and the dist-to-src mapping go beyond the brief's "exports"/"main"; they are added so a TS package whose main points at build output is still read correctly.
- A removed route is always breaking (it is reachable over HTTP) unless it moved (Unit 3). Removed lines of a schema file trip as before.
- Wildcard subpaths in "exports" (`"./*": "./src/*.ts"`) are matched as patterns.
- Every other removed or changed export is listed as the gate 2 check "internal signature changes" (pass, declared, since it rests on package.json), with each line and the reason per file. It does not trip the gate. "Every other" means: a private package, a module outside every package when the repo has other manifests, or a non-entry module of a published package.
- When reach cannot be read, the export is listed under "export reachability" (unverifiable, assumed) and routes to a human, never passing silently (W 2): no repo, an owning package.json that does not parse, or a repo with no package.json at all.
- "Lower confidence one notch" lowers the reported confidence one step, and the reason is listed. The measured level, which alone can shift the mode (W 2), is not touched. applyPolicy takes these as `notches`, and Unit 5 reuses them.
- Effect: PR 1 (server/src/metrics.ts, private `server`) and PR 7 (packages/engine-suite, private) now pass gate 2, and both stay Human on the grid. PR 5 is unchanged: it removes five routes. PR 9 does not pass gate 2, unlike the expectation: its one export (apps/api/src/infrastructure/observability/openobserve.ts@504f75e:245, private `@arcade/api`) is now internal, but it also edits entries in the metrics catalog, which the gate 2 ruling above treats as an event schema. Its mode is unchanged.

### Unit 5: required CI checks are measured, not assumed
- `bun run export` (src/export.ts) writes required-checks.json beside pr.json: `{ "checks": [...], "source": "..." }`. The checks are the union of branch protection's `required_status_checks` (contexts and checks) and repository rules of type `required_status_checks` on the PR's base branch. `GET .../branches/{base}/protection` needs admin rights; when it is refused, the readable `GET .../branches/{base}` summary (its `protection.required_status_checks`) is used instead. `source` records each endpoint's answer. The file is not written when no endpoint answers, so the brief falls back to the old assumed behaviour instead of reading "no answer" as "none required". For tests, a fixture `x.json` takes its required set from `x.required-checks.json`.
- The required set is today's configuration, read at export time, not the configuration when the PR ran. The export does not show past branch settings.
- Gate 1, with a rollup and a required set: a required check that is red trips and blocks (measured). A required check that is pending or absent from the rollup is unverifiable and routes to a human. An empty set gives "no required checks configured" (measured), and CI cannot block. Red checks that are not required are listed as "advisory CI checks" (pass, declared, from the rollup). Each lowers the reported confidence one notch (not the measured level), and each becomes a brief reason whose basis is named (the rollup and required-checks.json), not "something missing".
- Green for a required check means SUCCESS, NEUTRAL or SKIPPED, because GitHub counts all three as passing a required check. The brief said "conclusion other than SUCCESS"; this follows GitHub's merge rule instead. A check still running (conclusion empty, or state PENDING or EXPECTED) is pending.
- No required-checks.json: as before, every rollup check is treated as required, now tagged assumed. No rollup: unverifiable, routed to a human, as before.
- Effect: all 21 arcade exports have required-checks.json with no required checks (`main` is unprotected and has no rules). PR 11, 15, 16 and 20 go Block -> Human: their red "flag contract" and "rollout readiness" checks are advisory, and the grid (high damage x long window) gives Human. PR 11's gate 1 still routes to a human, for its hardcoded URLs, not for CI. PR 13's CI check goes from declared to measured.

### Unit 6: the model may fill an assumed signal with a cited one
- **Deviation from the write-up's one-way rule.** W 2 says missing data rounds toward caution, and W 3 says the probability shift "never moves the other way". Here a model answer may move an assumed signal one step either way, including toward release. The argument: the write-up rounds *missing* data toward caution; a line cited from the diff or the repo, which code has checked exists, is not missing data; the one-way rule still holds for measured facts, which the model never sees or changes. Confidence still only moves down from a model answer, never up.
- Accepted proposals feed the decision like any signal, so a Reach or Detection move can loosen the mode, e.g. high to low reach can take a change from Human to Staged. Code checks that a citation exists (and that a base-side cite names this diff's base), not that it supports the claim. The relevance check is the model's one sentence, shown beside the citation in the brief for the human to judge. (Narrowed by Round 4, Unit 2: a citation must also sit in the signal's citation domain and may not be the evidence of a measured conclusion it contradicts. Whether the line supports the claim is still the reader's call.)
- The note of an assumed signal is sent as its "why assumed". Some notes quote measured facts, e.g. the Reach note names the endpoints the calls reach. The model sees those facts as context; it cannot change any measured signal.
- One call (purpose "model contract") replaces the separate failure-mode and coherence calls. Input: the diff with head line numbers (base numbers for removed lines), the base sha, the PR title, body and commit message, and the assumed signals that have a scale, each with its value, scale and why it is assumed. Measured and declared signals, gate results and the mode are not sent. Output (strict JSON schema): `proposals[]` (signal, "no change" or "propose", value, cite, reasoning), `failure_modes` {modes, reason} and `coherence` {coherent, mismatches}. Reason wording (two sentences per evidenced reason) stays a separate call: it was not one of the two reads.
- Scales (src/policy.json `model.scales`, cautious to favourable): Path live < unreached; Reach high < low < none; Detection apparatus slow < fast; Time to revert full build and deploy < one-click rollback. "measured pipeline under 15 minutes" is left off the time-to-revert scale, because a cited line cannot measure a duration (CI run history is not an input). An assumed signal with no scale (History, review depth, the LLM reads themselves) is not offered to the model, and a proposal for it is refused.
- Code accepts a proposal only if the signal is assumed, the value is on its scale, the value is within one step of the current one, the cited `path:line` (head) or `path@sha7:line` (base) resolves to a non-blank line, and it is the first proposal for that signal. Accepted: the value is replaced, the source becomes "model (cited)", the evidence is the citation (quoted in the brief) and the note keeps the reasoning and the old assumed value. Refused: listed under Disagreements with the reason, and like every disagreement it lowers confidence one step. (Superseded by Round 4, Unit 2: a refusal names its rule and does not lower confidence.)
- The model sees values after the missing-data policy has rounded them, as the brief shows them. Confidence is computed from the signals before accepted proposals are applied, so filling an assumed input never raises it. The one-unknown search flips only assumed signals, so a signal the model filled is no longer offered as the unknown.
- No API key, or a secret found by gate 1: no call. Every assumed signal stays assumed, both reads are "unavailable", and the brief is unchanged (the golden out/pr13.md is rendered without a key).

## Round 4: after the first live model run

Standing decisions from the owner, not reopened here: the model may fill assumed signals and the grid may move as a result; the model-written top-reason prose stays; the scratchpad call logs stay.

### Unit 1: nothing secret leaves the process
- The live PR 1 run sent `OPENOBSERVE_PASSWORD` to the API: gate 1 scanned only added lines, while the payload also carried context lines. Now the gate 1 secret and PII scanners (src/gates.ts `sensitiveSpans`) run over the complete payload of every call in `askJson`: system prompt and user prompt, so the diff (added, removed and context lines), the PR title and body, the commit message, signal notes and the cited lines quoted for reason wording. Each value found is replaced with `[REDACTED:<kind>]` (kinds: private key, AWS key, GitHub token, Slack token, API key, JWT, URL credentials, credential, email, SSN, card number). The call log records the request as sent, after redaction, with the list of kinds replaced.
- A private key's BEGIN line opens a block: the base64 lines up to its END line are redacted too, because only the BEGIN line matches a pattern.
- Files whose name matches `.env*`, or whose name is secret(s) or credential(s) with any extension, are dropped from the payload entirely: their diff sections are cut from the contract prompt, and reason wording sends "(not sent: sensitive file)" in place of a quoted line from them. `secretsView.ts` is not such a file: the name must be the whole stem.
- A hit on an added line is a gate 1 trip as before, and no call is made. A hit on a context line or a removed line (present at base, not added by the PR) is not a trip: it is redacted, and the brief lists the measured signal "Secrets present at base" = observed with each file:line and kind, under Confidence and in the provenance table, worded "present in the repo before this change, not added by it". It does not lower confidence. The signal is listed only when observed, so briefs with no hit are unchanged. It is computed with or without a key, because it is measured from the diff, not from the call.
- Hits from all of a sensitive file's lines count, although the file is not sent: the brief should say the value is there. Hits in the PR title, body or commit message are redacted but not listed, because they have no file:line.
- The credential-assignment rule now also reads bare values (`KEY_PASSWORD=value`, as in env files); the PR 1 password is bare, so the old quoted-only rule missed it. A bare value ends at whitespace, a comma or a semicolon, so `password: hash(x)` is not one. A bare value that names another value (`$VAR`, `%VAR%`, or a property path like `process.env.FW_PROJECT_API_KEY!`) is not a secret: without this rule PR 11 went Human -> Block on two such lines.
- Effect: PR 1, 2, 5 and 11 list `.env.example` lines (credential, email or URL credentials), PR 5 also lists a database URL in `apps/api/src/infrastructure/db/client.ts`, PR 2 and 5 list `docker-compose.yml`, PR 7 and 15 list `scripts/dev.sh`, PR 8 lists `docker/compose.dev.yml`. No mode or gate result changes on the 21 PRs. tests/payload.test.ts runs PR 1 through `buildBrief` against a local stand-in for the API and checks the password value is absent from every request body; tests/fixtures/pr1.json is a copy of the PR 1 export.

### Unit 2: a citation must belong to the signal it supports
- Source: the Round 4 brief. On the live runs code accepted a stylesheet line as evidence that reach was low (PR 10), and the flag read `App.tsx:533` as evidence of both low reach and one-click undo, although the same line is the evidence for the measured "flag partial" (PR 13).
- Citation domains (src/model.ts `DOMAINS`), checked after the existing rules (assumed only, on the scale, one step, the line exists):
  - Reach: a code line on the measured path, or a route or handler definition. "Code" is a file with a code extension that is not a non-code kind (Unit 2 of Round 3). "On the measured path" means a changed file whose import chain reaches an entry point, or any importer on that chain. A route or handler definition is a line gate 2 already reads as a route (`path === "/..."`, a router call, `<Route path=...>`) or a handler the reach signal found.
  - Time to revert: a line in a workflow, compose file or script (Round 3 non-code kinds), or in a config or script file (yaml, json, toml, ini, conf, cfg, sh) whose name contains deploy or rollback; source code named deploy* is not one.
  - Path: an entry point file, a route line, or an import line in a file on the measured path.
  - Failure mode: an added or removed line of code. Failure mode has no scale today, so this domain has no effect yet; it is defined so a scale added later starts with one.
  - A signal on a scale with no domain (Detection apparatus) gets no citation at all: such a proposal is refused.
- The measured-evidence rule (`RULES_OUT`): while a measured signal holds a given conclusion, its own evidence lines cannot support moving certain signals toward release. Two entries:
  - Feature flag not "full" rules out Reach, Time to revert and Path. A flag that does not cover the whole change cannot show that the change reaches fewer systems, is unreached, or is undone in one click.
  - Reversible or irreversible = irreversible rules out Time to revert: rolling back code does not undo a write.
  - The spec names whole-change coverage and one-click undo. Path under the flag rule and the irreversible rule go one step further, on the same reasoning: a line that is evidence for a measured conclusion cannot argue the opposite.
  - Only a move toward release is checked. A move toward caution loosens nothing, so it cannot contradict a measured conclusion. The table names conclusions, not repos or files.
- When both rules refuse one proposal, both are named. Every refusal now names its rule: assumed signals only, scale, one proposal per signal, one step, citation exists, citation domain or measured evidence.
- Refusals are listed under Disagreements and no longer lower confidence: code kept the assumed value, so nothing the decision rests on changed. This supersedes the Round 3 Unit 6 line that a refusal lowers confidence like any disagreement.
- `buildBrief` takes an optional `ask` (a stand-in for the model call). When it is given, the model counts as available, so tests/citation.test.ts runs a canned answer through the whole chain on PR 13.
- Effect without a key: none. No mode or gate result changes on the 21 PRs, and out/pr13.md is unchanged.

### Unit 3: the brief shows the model's evidence where the reader looks
- On the live PR 10 and PR 13 runs, reason 1 said "the reach is low (model (cited))" but listed the path's lines as its evidence; the model's citation and its sentence were only in the provenance table.
- A reason rests on a model (cited) signal when it names or uses it: the damage reason uses Path and Reach (both when damage is high, the one it names when low); the window reason uses Detection apparatus, and Time to revert unless a flag covers the whole change (then the flag, not the revert, decides undo). `applyRuling` keeps the replaced value and its evidence on the signal (`model.was`), so the decision can show them.
- Under such a reason the evidence opens with the model's cited line (quoted, labelled "the model's citation for <signal>, which was <old value> (assumed)"), then "Model's reasoning: <its sentence>", then the lines the old assumed value rested on, each labelled. Then come the reason's other evidence lines, without repeats. The citation counts as the reason's line, so "no line to cite" is not printed under it.
- Labels: "contradicts the proposal" when the proposal says nothing is reached (Reach = none, Path = unreached) while those lines show something is; "superseded by the model's citation" otherwise. The prefix is "measured" for a line in code and "declared" for a line in a workflow or other config file, so the old Time to revert evidence (a declared job timeout) is not called measured.
- The provenance row is as before: "model (cited): <sentence> Was "<value>" (assumed): <old note>".
- Confidence lines: a line that names a filled signal as "<value> (assumed)" is reworded to say the model filled it, from what to what, and that confidence is computed before a fill. Today no fillable signal is a probability signal, so no such line appears on the 21 PRs; the rewrite is a guard, covered by a unit test.
- Effect without a key: none (no reason rests on a model (cited) signal); out/pr13.md and the 21 modes are unchanged.

### Unit 4: coherence items are checked against the diff
- On the live PR 1 run one coherence item said the `.env.example` change "includes real credentials". The values were already there at the base commit, and the item still counted toward low confidence.
- The coherence answer is now structured: each mismatch is `{text, claim, subject}`, where claim is "adds", "removes", "includes credentials" or "other", and subject is the exact text from the diff for adds and removes. Code checks the claim (src/model.ts `unsupportedClaim`):
  - adds X: X (whitespace and case normalised) is on an added line, or is the path of an added file;
  - removes X: X is on a removed line, or is the path of a deleted file;
  - includes credentials: gate 1 found a secret on an added line;
  - other: not checked, kept.
- An adds or removes item with no subject asserts something it does not name, so it is dropped.
- The model's label is not trusted for credentials. An item whose text says the change adds, includes, commits, contains, exposes or leaks real, actual, live, plaintext or hardcoded credentials, passwords, secrets, API keys or tokens is checked as "includes credentials", whatever claim it carries. A feature such as "adds a password reset flow" is not caught, because it names no value.
- A gate 1 secret on an added line withholds the call (Unit 1), so a credentials claim can never be supported while a call is made. On these inputs every such claim is dropped, which is the intent: a value present at base was not added by the change.
- A dropped item is listed under Disagreements as `model claim not supported by the diff: "<text>" (<why>)` and does not lower confidence. The coherence signal keeps only the supported items, and its note gives the dropped count. If every item is dropped, the read is coherent: a mismatch the diff does not support is not a mismatch. If the model says "not coherent" but names no item, that answer stands as before.
- Effect without a key: none.

## Demo: a page that re-runs the decision (apps/demo)

### Unit 1: measure and decide
- `buildBrief` is now `decide(measure(repo, range, pr, prFiles))` (src/run.ts). `measure` does every git read and every ts-morph pass: the diff, the PR export as loaded, the gates, the rule signals, the flag's line classes, the confidence facts, the detectors per failure mode, the failure-mode facts the model's answer is compared with, the commit messages and the diff text the model is shown, the citation context, the owner and whether CODEOWNERS exists. `decide` runs the model contract, the missing-data policy, the grid, the one unknown, the plan, reason wording and the markdown.
- `Measured` is plain JSON: the flag's line classes are kept as `[ref, class]` entries and the citation context's sets as arrays; decide rebuilds them. tests/measured.test.ts writes the PR 13 Measured to JSON, reads it back, checks it is equal, and checks decide on it renders out/pr13.md byte for byte.

### Unit 2: owner overrides and four switches
- `decide(measured, overrides?, modelKey?)` (src/overrides.ts). The CLI takes the same object as `--overrides '<json>'`: `{ "signals": { "<name>": "<value>" }, "model": false, "advisoryAsRequired": true, "stylesheetsCovered": true, "revertMinutes": 5 }`, every field optional.
- Owner values are applied before the model contract, so the model sees only signals still assumed. An assumed or declared signal is replaced: value as entered, source `declared by owner`, no evidence, note `declared by the owner; was "<old>" (<source>): <old note>`. A value equal to the current one changes nothing.
- A measured signal is not replaced. W 2: "Measured beats declared". The owner's value is listed as a disagreement, which lowers confidence one step like any other, and the measured value stands. This applies to "Secrets present at base" too.
- An owner value fills missing data, so the signal is no longer assumed: it is not rounded by the policy, it no longer lowers confidence as an assumed probability input, and the one unknown no longer offers it.
- An unknown signal name is an error rather than ignored. The two model reads (failure-mode second opinion, diff vs task) cannot be declared, because decide writes them after the overrides.
- `model: false`: no call even with a key. Both reads say "diff not sent to the LLM: the model is switched off" and no reason wording is added.
- `advisoryAsRequired`: every check in the PR export's rollup joins the required set (when the export has a required-checks.json; without one, every check is already treated as required). Gate 1's CI checks are recomputed by the same code (`withCiChecks`), so a red check trips and blocks, and the required set's source names the owner. A red check that is now required is no longer an advisory notch.
- `stylesheetsCovered`: added stylesheet lines that are outside the flag are counted inside it, and the flag signal is recomputed from the measured line classes. The default (off) is the Round 3 rule that stylesheets count as outside. The note gives the number of lines moved. The source becomes `declared by owner` only when this changes the value; otherwise the lines and the value are still measured, and the measured-evidence rule keeps applying.
- `revertMinutes`: Time to revert = "measured pipeline under 15 minutes" below 15 minutes (fast, per the undo-speed resolution), else "measured pipeline of N minutes" (slow), tagged declared by owner, note "the owner measured the build and deploy pipeline at N minutes". It is applied like an owner value, after the per-signal values, so it wins over one for Time to revert.
- `modelKey` is used for the model calls in place of ANTHROPIC_API_KEY (`askWithKey` in src/llm.ts). Calls made with it are not written to the log file: each is reported to a progress callback when it starts and when it ends, which is what the demo shows. The CLI never passes a key, so its calls are logged as before.
- `featureFlag` lost its unused `diff` parameter, so the flag can be recomputed from Measured.
- Effect without overrides: none; all 21 out/prN.md are unchanged. PR 13 with Reach low: low damage x long window = Staged, measured low confidence moves it to Human. PR 4 with a 5-minute revert: Staged -> Auto. PR 11 with advisory checks required: Human -> Block on gate 1. PR 13 with stylesheets covered: 49 lines move inside, the flag stays partial.

### Unit 4: the API
- apps/demo/server/app.ts, served by Bun.serve in apps/demo/server/main.ts (`PORT`, default 3000). At start it reads the 21 baked measurements and decides each baseline once. `GET /api/prs` lists number, title, mode and grid cell (`damage x window`). `GET /api/prs/:n` gives the baseline run, the range, the two read-only model signals and suggested values for the signals the decision tests. `POST /api/prs/:n/run` with `{ overrides, modelKey }` answers with server-sent events: `progress` per model call (start, and end with outcome, latency, tokens and estimated cost; never the prompt or the key), then `result` (brief, markdown, cell, the overrides, whether the model ran, and decide's time in ms), or `error`. The events come over the POST response rather than an EventSource, so the key travels in a request body and never in a URL.
- The server deletes ANTHROPIC_API_KEY from its environment when it loads (Bun reads .env from the working directory), so the model runs only with a key from the request, and only when the overrides do not switch it off. Calls made with that key report progress instead of writing logs/llm-calls.jsonl, so nothing the viewer sends reaches the disk.
- Request bodies are checked field by field (known override names, string values of at most 200 characters, booleans, a non-negative number of minutes); anything else is a 400. An unknown signal name comes back as an error event from decide.
- Every line quoted from the repo onto the screen goes through gate 1's `redact` (the quoter the server hands decide). The CLI's briefs are unchanged; the baseline still renders out/prN.md byte for byte, because none of them quotes a sensitive line.
- The event stream sends a comment every 5 seconds, and the idle timeout is 120 seconds, so a slow model call does not drop the connection.
